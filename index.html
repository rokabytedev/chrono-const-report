原始论断The Claim

在 macbook 上发现一个应该是编译器 bug。

如果我写 const auto t = chrono::<AnyClock>::now()。返回的时间是有问题的。

如果我把 const auto 改成 auto，就对了。

感觉应该是 constant folding 出了问题。花了老子半个小时琢磨为啥测出来的 performance 不对。

原文

这段话里包含三个彼此独立、都可以被单独证伪的命题：

#命题检验方式结果
P1const auto 版本得到的时间是错的行为测量未复现
P2改成 auto 结果就正确了行为测量 + 代码生成对照未复现
P3原因是常量折叠（constant folding）语言规则 + 编译器诊断可直接证伪

需要先说清楚的一点：他遇到的「测出来的 performance 不对」大概率是真的——这份报告不否认这件事。 本报告否认的是归因：把它算到 const 和常量折叠头上。第 07 节给出了几个能真实造成这种症状、 而且我在同一台机器上复现出来的原因。

02

证据一：编译器吐出来的机器码逐字节相同Identical Machine Code

这是最直接的一刀。写两个除了 const 之外完全一样的函数，放进同一个翻译单元、 用同一次编译产出汇编，然后比对。如果 P1、P2 成立，这里必须出现差异—— 因为「返回的时间不对」只可能来自不同的代码。

src/test3_asm.cpp

#include <chrono>
using namespace std::chrono;

extern void work();

long long elapsed_nonconst() {
    auto t0 = steady_clock::now();
    work();
    auto t1 = steady_clock::now();
    return duration_cast<nanoseconds>(t1 - t0).count();
}

long long elapsed_const() {
    const auto t0 = steady_clock::now();
    work();
    const auto t1 = steady_clock::now();
    return duration_cast<nanoseconds>(t1 - t0).count();
}

03

证据二：LLVM IR 层面同样相同Identical IR

汇编相同还可能被质疑成「后端把差异抹平了」。所以再往上看一层：LLVM IR， 在整条优化管线跑完之后、指令选择之前。常量折叠是一个 IR 层面的变换—— 如果它真的发生了，这里一定看得见。

$ clang++ -std=c++20 -O2 -S -emit-llvm test3_asm.cpp

--- elapsed_nonconst 函数体 ---
  %N = tail call i64 @_ZNSt3__16chrono12steady_clock3nowEv() #3
  tail call void @_Z4workv()
  %N = tail call i64 @_ZNSt3__16chrono12steady_clock3nowEv() #3
  %N = sub nsw i64 %N, %N
  ret i64 %N

--- elapsed_const 函数体 ---
  %N = tail call i64 @_ZNSt3__16chrono12steady_clock3nowEv() #3
  tail call void @_Z4workv()
  %N = tail call i64 @_ZNSt3__16chrono12steady_clock3nowEv() #3
  %N = sub nsw i64 %N, %N
  ret i64 %N

>>> 函数体 IR 完全相同 (IDENTICAL)
md5: nonconst = 916a606c8c579b13627207aadbd3ab7e
     const    = 916a606c8c579b13627207aadbd3ab7e

注意 IR 里两次 call now() 都原样保留着，一次都没被合并、没被外提、没被折叠。 Homebrew clang 20.1.5 的 IR 对照结果同样是完全相同。

严谨起见：两个函数的 define 行本身确实不同，但差异仅在 mangled 名 _Z16elapsed_nonconstv 与 _Z13elapsed_constv（长度前缀 16 与 13）。 上面比对的是函数体，md5 取自函数体。

结论

优化管线在两种写法上走了完全一样的路径。没有任何折叠、合并或重排发生在其中之一而不发生在另一个上。

04

证据三：常量折叠在这里物理上不可能Constant Folding Is Impossible Here

P3 是三个命题里最容易证伪的一个，而且它的证伪不依赖于任何测量——只要一行代码。

常量折叠的前提是「常量表达式」

编译器要折叠一个表达式，前提是它能在编译期求值，也就是这个表达式必须是 constant expression。 那就强制要求它是，看编译器怎么说：

$ cat test5_constexpr.cpp
#include <chrono>
using namespace std::chrono;
constexpr auto t = steady_clock::now();

$ clang++ -std=c++23 -O2 test5_constexpr.cpp
error: constexpr variable 't' must be initialized by a constant expression
    3 | constexpr auto t = steady_clock::now();
      |                ^   ~~~~~~~~~~~~~~~~~~~
note: non-constexpr function 'now' cannot be used in a constant expression
      |                    ^
/…/c++/v1/__chrono/steady_clock.h:34:21: note: declared here
   34 |   static time_point now() _NOEXCEPT;
      |                     ^

编译退出码: 1  （Apple clang 17 与 Apple clang 21 输出一致）

标准库里 now() 的声明就摆在那里：static time_point now() _NOEXCEPT;—— 没有 constexpr。编译器根本没有权限对它求值。

它甚至不是编译器能看穿的函数

更进一步，now() 在目标文件里是一个未定义的外部符号， 实现体在 libc++.dylib 里，编译单个 TU 时编译器连它的函数体都看不到：

$ clang++ -std=c++20 -O2 -c test3_asm.cpp -o test3.o
$ nm test3.o | grep -i now | c++filt

U  std::__1::chrono::steady_clock::now()
^ U = undefined，一个不透明的外部调用

而且它没有被标注 __attribute__((const)) 或 ((pure))。 这一点决定性地关闭了另一条路：编译器不被允许假设两次 now() 返回同样的值， 因此连公共子表达式消除（CSE）都做不了，更别说折叠成一个编译期常量。IR 里两次调用完好无损，正是这个规则的直接体现。

顺带澄清：const 在这里不给优化器任何新信息

  • 对局部变量而言，优化器手里有整个函数体，本来就完整知道这个变量有没有被改过。 加不加 const 不会给它任何额外的假设权限。
  • const 只是「承诺你不通过这个名字去修改它」，不是「这个值在编译期已知」。 后者是 constexpr / constinit 的活。
  • auto 推导会丢弃顶层 const：两种写法里 t 的推导类型 同为 steady_clock::time_point，前者只是多了个顶层 cv 限定符。这也是为什么 IR 会一模一样。
P3 证伪

常量折叠需要常量表达式；now() 不是 constexpr、不是 pure、在编译期是不透明外部符号。 这里不可能发生常量折叠，无论加不加 const。 这一条任何人都可以在自己机器上花 10 秒复现，不需要跑任何 benchmark。

07

那半小时到底撞见了什么What Actually Breaks Benchmarks

「测出来的 performance 不对」是个真问题，只是原因不在 const 上。 下面五个都是我在同一台机器上真实复现出来的、能造成这种症状的原因，按可能性排序。

A · 死代码消除：被测代码整段被删掉

如果被测函数的返回值没人用，-O2 会把它整个删掉。测出来是 0，然后你会觉得计时器坏了。

-O2，500 万次 sin 调用：
auto       + 丢弃返回值 :     0.0000 ms   <-- 循环被整段删除
const auto + 丢弃返回值 :     0.0000 ms   <-- 同样被删除
auto       + volatile   :     27.7323 ms
const auto + volatile   :     28.0530 ms

注意两种写法都是 0。但这里有个非常容易骗到人的陷阱：改代码时哪怕只是把 const auto 改成 auto，如果顺手动了别的东西——多打了一行 print、 多存了一个中间变量、把结果传给了某个函数——就可能刚好挡住了 DCE。 于是现象变成「改掉 const 就对了」，而真正起作用的是那个顺手的改动。这是最典型的假因果。

B · 冷启动：第一次测量普遍高 2.5–3.5 倍

刚编译出来的二进制，进程内的第一次测量会明显偏高（页错误、dyld 惰性绑定、缓存冷）。 在 12 组编译配置里 12/12 全部命中：

关键在于：独立的 clock_gettime 参照物也同步偏高， 说明这是真的慢了，不是 chrono 测错了。只要 A/B 两个版本在程序里有先后顺序， 先跑的那个就会背上这笔冷启动成本——而「先跑的那个」往往就是你先写的那个版本。 加上 warmup 之后，两者差异回到 0.5% 以内。

C · static const auto：唯一一个「加 const 就真的错」的写法

这是我在整轮实验里找到的、唯一能同时解释「加 const 出错」和「去掉 const 就好」的写法。 static 局部变量只在第一次执行到那一行时初始化：

static const auto t0 = Clock::now();   // 只在首次调用时采样！
work(n);
static const auto t1 = Clock::now();   // 同上

同一个函数连调 3 次：
  第 1 次调用:    10.5903 ms
  第 2 次调用:    10.5903 ms   <-- 时间点没有重新采样
  第 3 次调用:    10.5903 ms   <-- 永远返回第一次的结果

如果他的代码是这个形状，那「改掉 const 就好了」是真的——因为 static auto 同样会有这个问题，但很多人在删 const 的时候会把 static 一起删掉。原因是 C++ 的 static 存储期规则，不是编译器 bug， 也和常量折叠无关。

D · 命名空间作用域的 const：C++ 里 const 唯一真正改变语义的地方

在命名空间作用域，const 会给变量内部链接——放进头文件被多个 TU 包含时， 每个 TU 各持一份自己的拷贝；而去掉 const 会变成重复定义的链接错误，逼你改写法。 实测数值本身正确（都是程序启动时刻，不是 main 开始时刻），但多 TU 场景下语义会变。

  距 const auto 全局量:   208.21 ms
  距       auto 全局量:   208.20 ms
  // 数值都对，但 const 版是内部链接

E · 选错了时钟

system_clock 的 is_steady = 0——NTP 校时会让它跳变甚至倒退，不该用来做 benchmark。 本机实测确认 high_resolution_clock 就是 steady_clock（不是 system_clock）， 所以在 macOS 上用它计时没问题。

08

预判反驳Anticipated Objections

「你的编译器版本和我的不一样。」

测了三套：Apple clang 17.0.0（Xcode 26.3）、Apple clang 21.0.0（Command Line Tools）、 Homebrew 上游 LLVM 20.1.5。前两个是 Apple 分支，第三个和 Apple 分支血缘独立。 三套的汇编对照结果一致。

更关键的是：如果这真是某个版本的代码生成 bug，那么另外两个版本不可能生成字节相同的正确代码。 而且第 04 节的证伪根本不依赖版本——now() 不是 constexpr 是标准库的声明写死的。

「也许要开 LTO / -Ofast 才会出现？」

测了 -Ofast、-O3 -flto、-O3 -mcpu=native、 -Ofast -flto -mcpu=native。全部无差异，且 chrono 读数与独立参照物依然吻合到小数点后三位。

另外 LTO 也帮不上忙：now() 的实现体在 libc++.dylib 这个预编译动态库里， LTO 看不进去。

「也许不是折叠，是 CSE 把两次 now() 合并成一次了？」

这是个比原论断更合理的猜测，但同样不成立。编译器要合并两次调用，必须知道这个函数是 pure/const（无副作用且相同输入必返回相同输出）。steady_clock::now() 没有 任何这类属性标注，在目标文件里就是一个 U 的不透明外部符号。

而且这一点在 IR 里是直接可见的：第 03 节的 IR 里，两次 tail call now() 都完好保留， 一次都没被合并。两个版本都是如此。

「constant folding 明明是真实存在的优化。」

当然存在，而且很常见。但它的适用前提是常量表达式。 now() 是个运行期读硬件计时器的外部函数调用，不满足前提。

把 const（我不通过这个名字改它）和 constexpr（这个值编译期已知）混为一谈， 是这个论断的核心误解。前者不会、也不能触发常量折叠。

「const 不是能让编译器更激进地优化吗？」

对局部变量而言，基本不能。优化器手里有整个函数体，它自己就能看出这个变量有没有被修改过—— 你写不写 const，它掌握的信息量一样。const 主要是给人和类型检查看的。

而且 auto 的推导规则会丢弃顶层 const，两种写法推导出的类型同为 time_point，只是一个多了顶层 cv 限定符。这正是 IR 完全相同的原因。

「你没测我用的那个 clock。」

本机可用的三个标准时钟全测了。C++20 的 utc_clock / tai_clock / gps_clock / file_clock 在这台机器上的 Apple libc++ 里没有开放 （__cpp_lib_chrono = 201611），所以确实没测到。

但它们都建立在 system_clock::now() 之上，同样不是 constexpr。 更重要的是第 02–04 节的论证是结构性的——「const 不影响代码生成」和 「now() 不可折叠」这两条与具体是哪个 clock 无关。

「你是 Apple Silicon，我是 Intel Mac。」

补了一组 -arch x86_64 的 Rosetta 交叉验证（file 确认产物是 Mach-O 64-bit executable x86_64），结果同样无差异，chrono 与独立参照物吻合。

这不等同于原生 Intel 硬件，是这份报告的一个真实边界。但第 04 节的证伪与架构无关。

「你终究没跑我的那段代码。」

这条成立，是这份报告唯一真实的开口。我复现的是论断所描述的形状，不是原始代码本身。

但即便原始代码里真的存在一个 bug，本报告已经独立证明了：它的原因不会是常量折叠（第 04 节）， 也不会是 const 改变了代码生成（第 02、03 节）。第 07 节列了五个更可能的方向， 其中 C（static const auto）能同时解释「加 const 出错」和「去掉 const 就好」这两个现象。

把那段代码贴出来，我在同一台机器上照跑，有结果就更新这份报告。
